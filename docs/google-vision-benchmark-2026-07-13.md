# Google Cloud Vision 全数据集测试

生成时间：2026-07-13（Asia/Shanghai）

## 结论

Google Cloud Vision `DOCUMENT_TEXT_DETECTION` 在 14 张、625 道菜的数据集上完成 14/14 张识别：严格名称召回 90.7%，近似名称召回 93.9%。它与 PP-OCRv6 的总体质量基本打平，但在最困难的图片化、跨栏、中英文混排菜单上明显更好。

现在不能仅凭 OCR 原文召回决定生产模型。下一步应把 Vision 和 PP-OCRv6 的 OCR 结果分别交给同一个 Qwen 结构化，再使用现有 `scorePredictions` 比较最终“一菜一行”的菜名、价格和幻觉率。

## 测试口径

- 数据集：`/Users/kevin/Downloads/chopstory-test-data`
- 14 张菜单图片，625 条 gold 菜品。
- Feature：`DOCUMENT_TEXT_DETECTION`，语言提示 `zh`。
- 认证：本地 `gcloud` OAuth2 access token；普通 API key 实测被拒绝。
- 14 张图片同时请求，未出现 429 或其他 API 错误。
- 名称和价格评分口径与 PP-OCRv6 报告相同。
- 严格名称召回：完整 gold 菜名经 NFKC、大小写、空格和常见标点归一化后，能在该页 OCR 文本序列中找到。
- 近似名称召回：允许最多三条相邻 OCR 文本拼接，Levenshtein 相似度阈值 75%。
- 价格覆盖仅代表页面内不同价格数字 token 出现，不代表菜名价格已正确配对。

## 关键观察

1. Vision 在 `M001_P03`、`M001_P04`、`M001_P05` 三张最困难的高端菜单页上均高于 Paddle，说明其复杂版式 OCR 更有优势。
2. Paddle 在 `M002`、`M003`、`M005` 等普通密集文字菜单上略高，最终严格名称总数只比 Vision 多 2 条。
3. Vision 单张独立 POC 约 0.86–0.96 秒；14 张同时请求时 P50 上升到 6.50 秒，表明服务端存在并发排队。不过全批仍在 9.28 秒完成。
4. 同一张 `M001_P05` 独立运行时 Vision 严格召回曾达到 62.5%，全量并发运行时为 50.0%，说明 OCR 输出存在一定运行波动。最终报告只使用完整 14 张这一轮。
5. 两者都不能直接输出可靠的一菜一行结构；菜名经常被价格、重量和英文说明拆成多个文字块。

## 产品建议

暂不做双 OCR 供应商并行调用。按 Occam's Razor，先使用同一个 Qwen 结构化器分别测试：

- `Vision OCR -> Qwen -> 菜单 JSON`
- `PP-OCRv6 -> Qwen -> 菜单 JSON`

谁在最终结构化名称召回、价格准确率和幻觉率上胜出，就选谁作为主 OCR；另一家只作为故障切换候选。

Google Vision 生产部署必须使用服务账号 OAuth 或工作负载身份，不依赖本机 `gcloud`，也不能依赖当前普通 `GOOGLE_VISION_API_KEY`。

机器可读结果：`docs/google-vision-benchmark-2026-07-13.json`

可复现脚本：`scripts/google-vision-benchmark.mjs`
